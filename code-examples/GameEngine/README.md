# GameEngine — стартовый проект лабораторной работы

Консольное приложение моделирует небольшую игровую сцену: игрок перемещается
по карте, управляет здоровьем и золотом, переносит предметы и взаимодействует
с сундуком. Это не готовая игра, а рабочая библиотека игровых утилит, которую
нужно сделать удобнее с помощью методов расширения.

## Темы работы

- статические классы;
- статические методы;
- статические поля;
- методы расширения.

## Требования

- .NET SDK 9.0 или новее;
- Visual Studio 2022 либо .NET CLI;
- внешние пакеты не требуются.

## Открытие и запуск

Откройте `GameEngine.sln` в Visual Studio. В обозревателе решений проект
`GameEngine` расположен внутри папки решения `StarterProjects`.

Для запуска из командной строки перейдите в каталог с решением и выполните:

```bash
dotnet run --project GameEngine/GameEngine.csproj
```

Для проверки сборки:

```bash
dotnet build GameEngine.sln
```

## Сценарий

Junior-разработчик подготовил библиотеку игровых утилит. Она работает, но код
клиентского приложения перегружен вызовами следующего вида:

```csharp
PlayerUtils.Heal(player, 20);
InventoryUtils.AddItem(player.Inventory, item);
MapUtils.IsInside(map, x, y);
ChestUtils.Open(chest);
```

Ваша задача — сделать вызовы естественнее, не изменяя поведение программы.
Исходный проект намеренно **не содержит методов расширения**.

## Структура

```text
GameEngine.sln
├── StarterProjects                         (папка решения Visual Studio)
└── GameEngine/
    ├── GameEngine.csproj
    ├── Program.cs
    ├── Models/
    │   ├── Player.cs
    │   ├── Inventory.cs
    │   ├── Item.cs
    │   ├── Position.cs
    │   ├── GameMap.cs
    │   └── Chest.cs
    └── Utils/
        ├── PlayerUtils.cs
        ├── InventoryUtils.cs
        ├── MapUtils.cs
        ├── ChestUtils.cs
        └── GameSettings.cs
```

Классы из папки `Models` являются моделями данных и не должны получать методы
в рамках исходного решения. Поведение расположено в статических классах из
папки `Utils`.

## Как выполнять лабораторную

1. Запустите программу и проверьте пункты меню.
2. Просмотрите все методы в статических классах `Utils`.
3. Решите, какой объект является естественным получателем каждой операции.
4. Создайте отдельный статический класс или классы для методов расширения.
5. Перенесите подходящие методы, добавив параметру-получателю ключевое слово
   `this`.
6. Замените вызовы в `Program.cs` на вызовы в точечной нотации.
7. Соберите и снова запустите приложение.

Метод расширения должен повторять прежнюю логику. Не меняйте правила лечения,
ограничение золота, вместимость инвентаря или правила работы сундука.

## Примеры ожидаемого направления рефакторинга

Следующие пары показывают стиль результата, но не являются полным решением:

```csharp
PlayerUtils.Heal(player, 20);
// player.Heal(20);

InventoryUtils.IsEmpty(player.Inventory);
// player.Inventory.IsEmpty();

MapUtils.Distance(player.Position, chest.Position);
// player.Position.DistanceTo(chest.Position);

ChestUtils.Open(chest);
// chest.Open();
```

Подумайте, должен ли метод `MapUtils.ClampPosition(map, position)` читаться как
операция карты, позиции или оставаться вспомогательной статической функцией.
Возможны разные обоснованные решения, если они сохраняют ясность интерфейса.

## Методы, которые должны остаться статическими

Фабричные операции не имеют уже существующего экземпляра-получателя. Поэтому
следующие методы не следует превращать в методы расширения:

- `PlayerUtils.CreateDefaultPlayer`;
- `InventoryUtils.CreateStarterInventory`;
- `MapUtils.CreateDefaultMap`;
- `MapUtils.CreateCenterPosition`;
- `ChestUtils.CreateChest`.

Они создают объекты или являются операциями уровня типа, а не действием над
конкретным объектом.

## Статические поля

Класс `GameSettings` содержит изменяемые статические поля:

- `DefaultPlayerHealth`;
- `DefaultMapWidth`;
- `DefaultMapHeight`;
- `MaxInventorySize`;
- `MaxGold`.

Измените одно из них перед созданием игрока или карты и проследите, где новое
значение повлияет на работу программы. Объясните, почему эти значения являются
настройками уровня приложения, а не свойствами отдельного игрока.

3. Какие плюсы и риски дают изменяемые статические поля?
4. Как компилятор распознаёт метод расширения?
5. Почему метод расширения не добавляет метод в исходный класс физически?
6. В каких случаях обычный статический метод читается лучше метода расширения?
7. Какие методы в этом проекте вы преобразовали и почему?

## Критерии самопроверки

- Проект собирается без предупреждений и ошибок.
- В моделях нет добавленного поведения, не требуемого заданием.
- Все фабричные методы остались обычными статическими методами.
- Подходящие операции над игроком, инвентарём, сундуком и позициями используют
  методы расширения.
- Меню сохраняет исходное поведение.
- После рефакторинга в `Program.cs` стало меньше вызовов в форме
  `ИмяКласса.Метод(объект, ...)`.

## Сохранение поведения

При рефакторинге сравните следующие ситуации до и после преобразования:

1. Лечение не поднимает здоровье выше `MaxHealth`.
2. Урон не опускает здоровье ниже нуля.
3. Погибшего игрока нельзя вылечить текущим методом `Heal`.
4. Золото не превышает `GameSettings.MaxGold`.
5. Новый тип предмета нельзя добавить в полный инвентарь.
6. Количество существующего предмета можно увеличить, даже если инвентарь
   уже содержит максимальное число разных предметов.
7. Изъятие предмета с количеством ноль удаляет его запись из списка.
8. С предметами сундука можно работать только в открытом сундуке.
9. Координаты игрока перед перемещением ограничиваются границами карты.

Если один из сценариев изменился, причина обычно не в синтаксисе метода
расширения, а в перенесённой или продублированной бизнес-логике. В этом случае
верните общий код в одно место и снова запустите программу.

## Возможный порядок файлов после рефакторинга

Один из вариантов — создать папку `Extensions` и разместить в ней несколько
статических классов. Например, операции игрока можно собрать в
`PlayerExtensions`, а операции инвентаря — в `InventoryExtensions`. Каждый
такой класс остаётся статическим, как требует механизм методов расширения.

Не обязательно создавать один класс расширений на каждую модель. Важнее,
чтобы название класса и пространство имён были понятны, а методы не создавали
неоднозначность с существующими членами типов. Не добавляйте в модели методы,
если цель работы — отработать именно методы расширения.
