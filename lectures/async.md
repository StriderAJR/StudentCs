# Лекция: асинхронное программирование, параллелизм и многопоточность в C#

## Введение

Начать нужно с разрушения базового заблуждения. Почти все, кто впервые слышит про async/await, представляют это так: есть несколько ядер процессора, и каждая задача каким-то образом уезжает на отдельное ядро. Это неверная модель. Она приводит к систематическим ошибкам в коде и непониманию того, что вообще происходит.

Асинхронность не про ядра. Она вообще не про ускорение вычислений. Она про другое — про то, чтобы не держать поток занятым, когда он на самом деле ничего не делает.

> **Асинхронность** - это про то, чтобы не блокировать поток во время ожидания. 

> **Параллелизм** - это про одновременное выполнение на нескольких потоках.

Чтобы это понять, сначала нужно разобраться с базовыми сущностями.

### Потоки как фундамент

Любой код в программе исполняется потоком. Это единственная сущность, которая реально «выполняет строки кода».

У процесса есть память и ресурсы. Внутри процесса есть потоки. Каждый поток:

- имеет свой стек,
- выполняет инструкции,
- управляется операционной системой.

Важно зафиксировать: потоков обычно больше, чем ядер. Операционная система постоянно переключает ядра между потоками. Это переключение не бесплатное.

Создавать поток — дорого. Поэтому .NET использует ThreadPool — пул уже созданных потоков, которые переиспользуются. Когда нужно выполнить работу, она передаётся в пул, и какой-то поток её подхватывает.

### Что такое Task

Теперь появляется следующая абстракция - Task.

Task - это не поток. Это объект, который описывает операцию:
- выполняется ли она, 
- завершилась ли, 
- какой у неё результат 
- что делать после завершения.

Это описание работы, а не сама работа.

Именно здесь ломается интуитивная модель: наличие Task не означает, что где-то сейчас выполняется код.

## Блокирующий и неблокирующий код

Рассмотрим два варианта.

``` csharp
public static async Task Main()
{
    Console.WriteLine("=== Blocking ===");
    BlockingDemo();

    Console.WriteLine("\n=== Non-blocking ===");
    await NonBlockingDemo();
}

public static void BlockingDemo()
{
    Thread.Sleep(2000);
    Console.WriteLine("Done");
}

public static async Task NonBlockingDemo()
{
    await Task.Delay(2000);
    Console.WriteLine("Done");
}
```

В первом случае поток полностью остановлен. Он занят, но ничего не
делает.

Во втором случае поток освобождается. Метод приостанавливается, но поток
возвращается в пул и может выполнять другую работу.

Это ключевая идея асинхронности: не держать поток занятым впустую.

### Что на самом деле делает await

Рассмотрим код:

``` csharp
await DownloadSomething();
ParseDownloaded();
```

Интуитивно кажется, что поток «ждёт» внутри DownloadSomething. Но это не так.

Разворачиваем механизм:

1. Метод начинает выполняться на потоке
1. Доходит до await
1. Если задача не завершена:
    - выполнение метода приостанавливается
    - сохраняется его состояние
    - регистрируется продолжение: что делать дальше
1. Поток освобождается

### Критичный вопрос
Обычно в этот момент возникает вопрос:
если поток освободился, кто тогда выполняет DownloadSomething?

Разберём:
```cs
public async Task DownloadSomething()
{
    await httpClient.GetAsync("...");
}
```
Что происходит:

- поток формирует HTTP-запрос
- передаёт его операционной системе
- дальше сетью занимаются:
    - драйверы
    - сетевой стек
    - железо

CPU в этом не участвует.

Метод приостанавливается. Поток освобождается.

Когда ответ приходит:

- система сигнализирует runtime
- continuation ставится в очередь
- любой поток продолжает выполнение

В промежутке нет выполняющегося потока вообще.


## Последовательность и параллельность ожиданий

Теперь следующий шаг.

``` csharp
public static async Task Sequential()
{
    await Task.Delay(1000);
    await Task.Delay(1000);
    await Task.Delay(1000);
}
```
Здесь три ожидания идут подряд.

Теперь другой вариант:

``` csharp
public static async Task Parallel()
{
    Task t1 = Task.Delay(1000);
    Task t2 = Task.Delay(1000);
    Task t3 = Task.Delay(1000);

    await Task.WhenAll(t1, t2, t3);
}
```

Ни в одном из этих примеров нет дополнительных потоков.

Но второй вариант выполняется быстрее, потому что ожидания перекрываются.

Это важный переход:
асинхронность может давать выигрыш во времени без увеличения числа потоков.

### Реальный сценарий: запросы
```cs
public static async Task<string> GetDataAsync(int id)
{
    await Task.Delay(1000);
    return $"Data {id}";
}

public static async Task DemoRequests()
{
    List<Task<string>> tasks = new List<Task<string>>();

    for (int i = 1; i <= 5; i++)
    {
        tasks.Add(GetDataAsync(i));
    }

    string[] results = await Task.WhenAll(tasks);

    foreach (string r in results)
    {
        Console.WriteLine(r);
    }
}
```
Здесь каждый запрос — это ожидание. CPU почти не задействован.
Асинхронность позволяет не простаивать, а перекрывать ожидания.

## Ошибка: забыли await

``` csharp
public static async Task Fill(List<int> list)
{
    await Task.Delay(1000);
    list.Add(1);
}

public static async Task Demo()
{
    List<int> list = new List<int>();

    Fill(list);

    Console.WriteLine(list.Count);
}
```

Метод запущен, но не ожидается. Код идёт дальше, а данные ещё не готовы.

Это не вызов функции. Это запуск асинхронной операции.

## Deadlock — почему .Result опасен

До этого момента вся модель строилась на одной ключевой идее: await не блокирует поток. Он отпускает его, давая системе возможность использовать этот поток для другой работы.

Теперь рассмотрим, что происходит, когда в эту модель вмешивается синхронное ожидание.

``` csharp
public static string Get()
{
    return GetAsync().Result;
}

public static async Task<string> GetAsync()
{
    await Task.Delay(1000);
    return "OK";
}
```

На первый взгляд кажется, что `.Result` — это просто «подождать результат», аналогично await. Но это не так.

Представим, что этот код выполняется в UI-потоке (или в старом ASP.NET-контексте, где есть привязка к потоку).

1. Вызывается GetDataAsync. Метод доходит до await Task.Delay(1000).
2. Так как задача ещё не завершена, метод приостанавливается и регистрирует продолжение: «когда задача завершится — продолжить выполнение здесь же».
3. Важно: «здесь же» означает тот же самый поток, в котором метод начал выполняться.

И вот в этот момент вызывается `.Result`.

`.Result` делает простую вещь: он блокирует текущий поток, пока задача не завершится.

Дальше происходит критическая ситуация:

- задача завершилась и хочет продолжить выполнение метода
- продолжение должно выполниться на том же потоке
- но поток заблокирован .Result

Получается замкнутый круг:

- поток ждёт завершения задачи
- задача ждёт освобождения потока

Никто не может продвинуться дальше.

Это и есть deadlock.

Если тот же код написать через await, ситуация принципиально меняется:

```cs
public static async Task<string> GetData()
{
    return await GetDataAsync();
}
```

Теперь поток не блокируется. Он освобождается, и когда операция завершится — продолжение спокойно выполнится.

Здесь важно зафиксировать не синтаксис, а модель:

- `await` — это «приостановить и продолжить позже»
- `.Result` — это «стоять и ждать, не двигаясь»

Именно блокировка потока делает deadlock возможным.

## Переход к CPU-задачам

До этого момента все примеры были про ожидание: сеть, таймеры, ввод-вывод. В этих сценариях поток большую часть времени просто не нужен, потому что реальная работа происходит вне CPU. Именно поэтому async/await даёт эффект — он освобождает поток в те моменты, когда делать на нём нечего.

Теперь рассмотрим принципиально другой тип задач — вычисления.

``` csharp
public static int CpuWork()
{
    int sum = 0;

    for (int i = 0; i < 100_000_000; i++)
    {
        sum += i;
    }

    return sum;
}
```

Здесь нет ожидания. Здесь есть чистая работа CPU.

И в этот момент важно не сломать модель, которую уже выстроили.

До этого await означал: "мы ждём внешнюю операцию и освобождаем поток".

Но для CPU-задач такого механизма нет. Нельзя «подождать вычисление, не занимая поток», потому что вычисление и есть работа потока.

Поэтому здесь появляется новый инструмент:

``` csharp
await Task.Run(() => CpuWork());
```
И это принципиально другой случай, не связанный с тем, что было раньше.

Если раньше Task представлял собой I/O-операцию (например, HTTP-запрос), то здесь Task.Run создаёт эту задачу сам.

Что происходит:

- берётся делегат CpuWork
- он отправляется в ThreadPool
- один из потоков пула начинает его выполнять

То есть:
> мы вручную говорим системе: выполни этот код в другом потоке

Это уже не «асинхронность ради ожидания», а явное использование многопоточности.

Важно зафиксировать различие:

- `await Task.Delay(...)` — поток освобождается, потому что идёт ожидание
- `Task.Run(...)` — поток создаётся (или берётся из пула), потому что есть работа

Теперь ключевой момент.

Если написать так:

```cs
await Task.Run(() => CpuWork());
await Task.Run(() => CpuWork());
```
то, несмотря на использование потоков, код всё равно выполняется последовательно.

Почему:

- первый await останавливает выполнение метода
- вторая задача даже не запускается, пока первая не завершится

В итоге:

- задачи выполняются по одной
- в каждый момент времени работает один поток
- ускорения нет

Это важный переход в мышлении:

> наличие потоков ≠ параллелизм

Чтобы получить параллелизм, нужно не просто использовать Task.Run, а запускать несколько задач до ожидания их завершения.

Можно сделать так, как делали раньше:
``` csharp
Task<int> t1 = Task.Run(() => CpuWork());
Task<int> t2 = Task.Run(() => CpuWork());

await Task.WhenAll(t1, t2);
```

Теперь задачи запускаются одновременно. ThreadPool выделяет для них потоки, и если у процессора есть несколько ядер, вычисления действительно идут параллельно.

Здесь появляется новое качество: не просто "не блокировать поток", а использовать несколько потоков одновременно.

Это уже не асинхронность, а параллелизм.

### Почему Task неудобен для массовых задач

Если задач немного, такой подход работает нормально. Но если их десятки или сотни, код начинает разрастаться:

- нужно вручную создавать задачи
- нужно управлять их списком
- нужно явно вызывать WhenAll

При этом реальная цель — просто выполнить одну и ту же операцию много раз.

И здесь появляется следующий уровень абстракции.

## Parallel — специализированный инструмент для CPU

К этому моменту уже понятно, что для вычислений одного лишь async/await недостаточно. Он не ускоряет CPU-задачи, потому что по своей природе решает другую проблему — ожидание.

Мы уже увидели, что можно вручную запускать задачи через Task.Run и затем ожидать их через Task.WhenAll. Это работает, но у такого подхода есть ограничение: он требует ручного управления.

Если задача представлена в виде цикла или большого количества однотипных операций, такой код быстро становится перегруженным и теряет читаемость. Кроме того, приходится самому думать о том, сколько задач запускать, как их группировать и как учитывать количество доступных ядер.

Именно здесь появляется Parallel.

``` csharp
Parallel.For(0, 10, i =>
{
    CpuWork();
});
```

Смысл этого инструмента в том, что разработчик описывает что нужно сделать, а не как именно распределить работу по потокам.

Дальше уже сам .NET:

- разбивает диапазон на части
- распределяет эти части по потокам ThreadPool
- учитывает количество доступных ядер
- балансирует нагрузку

То есть управление параллелизмом поднимается на более высокий уровень абстракции.

Важно при этом не перепутать модели. В отличие от async/await, здесь нет ожидания внешнего события. Здесь есть чистая работа CPU. Поэтому Parallel.For блокирует вызывающий поток до завершения всех вычислений.

Это нормальное поведение: поток не простаивает, он участвует в выполнении работы.

## Переход к многопоточности

До этого момента потоки в основном были скрыты за абстракциями:

- ThreadPool управлял ими автоматически
- Task позволял описывать работу
- Parallel распределял нагрузку

Но при этом разработчик напрямую потоками не управлял.

Теперь можно убрать эти абстракции и посмотреть, как выглядит базовый уровень.

``` csharp
Thread thread = new Thread(() =>
{
    Console.WriteLine("Hello");
});

thread.Start();
thread.Join();
```

Здесь создаётся реальный поток операционной системы.

В этот момент исчезает вся «магия» фреймворка.
Нет автоматического распределения, нет балансировки, нет защиты от ошибок. Всё управление ложится на разработчика.

И именно здесь появляется следующая фундаментальная проблема.

### Гонка данных
Как только в системе появляется несколько потоков, они начинают работать с одними и теми же данными. И это мгновенно приводит к некорректному поведению.

Рассмотрим простой пример:

``` csharp
int counter = 0;

Parallel.For(0, 1000, i =>
{
    counter++;
});
```

Интуитивно кажется, что результат должен быть равен 1000. Но на практике он почти всегда будет меньше.

Причина в том, что операция counter++ не является атомарной. Она состоит из нескольких шагов:

- прочитать значение
- увеличить
- записать обратно

Если два потока делают это одновременно, один из результатов теряется.

Это называется гонкой данных — ситуация, когда результат зависит от того, в каком порядке выполнились операции в разных потоках.

### Синхронизация
Чтобы устранить эту проблему, необходимо явно контролировать доступ к общим данным.
``` csharp
int counter = 0;
object locker = new object();

Parallel.For(0, 1000, i =>
{
    lock (locker)
    {
        counter++;
    }
});
```

Здесь вводится блокировка. В каждый момент времени только один поток может войти в критическую секцию и изменить значение.

Теперь результат будет корректным.

Однако появляется новая цена — снижение параллелизма. Потоки начинают ждать друг друга. Это неизбежный компромисс между скоростью и корректностью.Теперь доступ защищён.

## Итог

Асинхронность решает задачу ожидания. Она позволяет не держать поток занятым, когда работа фактически не выполняется.

Параллелизм решает задачу ускорения вычислений. Он использует несколько потоков и несколько ядер.

Многопоточность — это более низкий уровень, где разработчик сам управляет потоками и отвечает за корректность работы с данными.

И ключевое различие, которое важно помнить:

асинхронность — это про эффективность использования потоков
параллелизм — это про одновременное выполнение
многопоточность — это про управление и ответственность
